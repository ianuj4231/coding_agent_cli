SINGLE AGENT VS MULTI-AGENT: THE INTUITION
============================================

The real question is:

Does the work need one person using several hands, or several people
independently investigating?


1. MULTIPLE TOOLS ARE NOT MULTIPLE AGENTS
------------------------------------------

Imagine one chef preparing two sandwiches.

The chef already knows exactly what needs to happen, so they tell two machines:

- Machine 1: toast bread A.
- Machine 2: toast bread B.

Both machines can operate simultaneously.

This resembles one LLM response containing the same tool twice:

    create_file("add.py")
    create_file("subtract.py")

The LLM has already made the important decisions:

- Which files are required
- What their names should be
- What content they should contain

The tools simply perform those instructions.

Parallel tool calling therefore means:

    One decision-maker dispatches multiple known operations simultaneously.

It provides parallel execution, not parallel investigation or reasoning.


2. WHAT MULTIPLE AGENTS PROVIDE
-------------------------------

Now imagine the chef receives this objective:

    Design food for a three-day international wedding. Handle allergies,
    costs, regional preferences, kitchen capacity, and serving logistics.

This work contains several large areas, each requiring discovery and judgment:

- One person investigates allergies.
- One designs the menu.
- One estimates costs.
- One plans kitchen logistics.
- One checks whether the complete plan is practical.

Each person does more than perform one predefined operation. Each receives an
objective, investigates, makes decisions, changes direction, and returns a
conclusion.

That resembles multiple agents.


3. TOOL VS AGENT
----------------

A tool receives a reasonably well-defined instruction:

    Create add.py with this content.

Most of the important thinking is already complete.

An agent receives a problem:

    Investigate whether the authentication system is secure.

The agent must still decide:

- Where should I begin?
- Which files are relevant?
- What should I search for?
- What did the search reveal?
- What should I inspect next?
- Is this actually a vulnerability?
- Do I have enough evidence?

During that investigation, one security agent might make many model calls and
many tool calls.

Therefore:

    Tool  = a capability that performs an operation.
    Agent = a decision-maker that repeatedly chooses and uses capabilities.


4. PARALLEL TOOLS VS MULTIPLE AGENTS
------------------------------------

Parallel tools execute branches of a known plan.

Multiple agents independently discover and execute their own plans.

Parallel tool calling may look like this:

    One agent
       |-- create_file("add.py")
       |-- create_file("subtract.py")
       `-- create_file("multiply.py")

The agent already knows all three actions.

Multi-agent work may look like this:

    Coordinator
       |-- Security agent
       |     `-- its own reasoning and tool-use loop
       |-- Performance agent
       |     `-- its own reasoning and tool-use loop
       `-- Testing agent
             `-- its own reasoning and tool-use loop

The coordinator knows the objectives, but it does not necessarily know every
tool call that each specialist will eventually need.


5. KNOWN WORK VS DISCOVER-AS-YOU-GO WORK
-----------------------------------------

Suppose the request is:

    Create add.py and subtract.py.

The work is known immediately. The agent can request both tool calls in one
model response.

Now suppose the request is:

    Find important security and performance problems.

The coordinator cannot know every required operation at the beginning. Each
investigation changes direction based on what it discovers.

The security branch might behave like this:

    Search authentication
        -> inspect token handling
        -> discover unusual permissions
        -> investigate authorization
        -> verify the finding
        -> report

The performance branch might behave like this:

    Inspect retrieval
        -> discover slow queries
        -> inspect caching
        -> examine embedding calls
        -> identify bottlenecks
        -> report

Each branch contains its own adaptive loop:

    Observe -> decide -> act -> observe again -> change direction

Multiple agents allow entire evolving investigations to happen concurrently.
That is different from merely running Tool A and Tool B simultaneously.


6. COULDN'T ONE AGENT DO ALL OF THIS?
-------------------------------------

Yes.

A capable single agent can investigate security, performance, testing, and
architecture sequentially. Multi-agent architecture is rarely required because
a single agent is incapable of doing the work.

Multi-agent architecture becomes useful when separating the work creates a
practical advantage:

- Independent investigations can proceed concurrently.
- Each specialist receives a clean working context.
- Different agents can receive different instructions and tools.
- Large amounts of information do not compete inside one context.
- One agent can independently review another agent's conclusion.
- Different permission boundaries can be enforced.

It is an engineering trade-off, not an automatic intelligence upgrade.

Ten agents are not automatically smarter than one agent. Sometimes they are
merely ten agents producing duplicated work that another agent must reconcile.


7. WHEN TO USE A SINGLE AGENT
-----------------------------

Use a single agent when the request has one connected reasoning journey.

Example:

    Explain how semantic caching works in this project.

The journey might be:

    Search for cache
        -> discover the orchestrator
        -> read the orchestrator
        -> discover invalidation logic
        -> read the watcher
        -> connect the findings
        -> explain

Several files and tools are involved, but all steps belong to the same connected
investigation. Later decisions depend on earlier discoveries.

Use a single agent when: (imp)

- There is one primary objective.
- The parts strongly depend on one another.
- One agent can hold the relevant information comfortably.
- The user expects a quick answer.
- One consistent understanding is important.
- Independent verification is unnecessary.
- Different permission boundaries are unnecessary.

Advantages of a single agent:

- Simpler architecture
- Lower model cost
- Usually lower latency
- One continuous understanding of the problem
- Easier memory and session management
- Easier debugging
- No conflicting agent conclusions
- No coordinator required

Disadvantages of a single agent:

- Large investigations can overload its context.
- Independent workstreams may happen sequentially.
- The same agent must cover every speciality.
- It may accept its own mistaken conclusion.
- A long investigation can become unfocused.


8. WHEN TO USE MULTIPLE AGENTS
------------------------------

Use multiple agents when the request contains separate, substantial workstreams
and each workstream needs its own adaptive investigation.

Example:

    Perform a production-readiness assessment covering security,
    performance, testing, architecture, and deployment.

This contains several distinct questions:

1. Is the application secure?
2. Is it performant?
3. Is it adequately tested?
4. Is its architecture maintainable?
5. Can it be deployed safely?

These investigations are substantial, mostly independent, able to run
simultaneously, and easier to manage in separate contexts. A coordinator can
then combine the findings into one prioritized report.

Use multiple agents when:

- The request contains several genuinely independent objectives.
- Each objective requires its own multi-step investigation.
- The investigations benefit from running concurrently.
- Each branch produces a large amount of context.
- Specialist instructions or tools are valuable.
- Separate permission boundaries are needed.
- Independent review provides meaningful value.

Advantages of multiple agents:

- Independent investigations can happen concurrently.
- Each agent concentrates on one domain.
- Each agent receives a cleaner working context.
- Agents can have different tools and permissions.
- A reviewer can challenge another agent's conclusions.
- Large problems can be reduced to specialist summaries.
- A failure may be isolated to one workstream.

Disadvantages of multiple agents:

- More model calls and higher cost
- More coordination logic
- Agents may duplicate searches
- Findings may conflict
- Final synthesis can lose details
- Shared state is harder to manage
- Concurrent file edits can collide
- Human approval becomes more complicated
- Debugging becomes harder
- Parallelism does not help when tasks depend on one another


9. THE DEPENDENCY TEST
----------------------

These calls are independent:

    create_file("a.py")
    create_file("b.py")
    create_file("c.py")

One agent can request all three simultaneously.

These operations are dependent:

    Search for authentication
        -> use the result to identify a file
        -> read that file
        -> use its contents to identify a vulnerability
        -> inspect related authorization logic

They cannot all be requested in the first model response because later actions
depend on earlier results.

A specialist agent can independently handle this entire adaptive chain.
Multiple specialist agents allow several such chains to run concurrently.


10. PRACTICAL DECISION QUESTIONS
--------------------------------

Do not ask, "How many tools are needed?"

Instead, ask:

1. Is there one objective or several independent objectives?

   One connected objective usually means one agent. Several substantial,
   independent objectives may justify multiple agents.

2. Are the exact operations already known?

   If the exact tool calls are already known, parallel tools are enough. If each
   branch must investigate and choose its own next steps, multiple agents may
   help.

3. Do the branches depend heavily on one another?

   If branch B needs branch A's result, splitting them provides little
   parallelism. If they can progress independently, multiple agents become more
   useful.

4. Will each branch generate a lot of context?

   If everything fits comfortably inside one context, prefer one agent. If each
   investigation produces many files, logs, and findings, separate contexts may
   help.

5. Is independent judgment valuable?

   It may not be necessary for an ordinary explanation. It can be valuable for
   security reviews, release approval, or other high-risk decisions.

6. Does the benefit justify the coordination cost?

   Multi-agent architecture should measurably improve quality, coverage,
   latency, or reliability. Otherwise, prefer one agent.


11. THREE SIMPLE EXAMPLES
-------------------------

Example A: Definitely single agent

    Where is long-term memory stored, and how is it loaded?

This is one connected subject. One agent can search, inspect, connect, and
answer.

Example B: Single agent with parallel tools

    Create three independent files for addition, subtraction, and
    multiplication.

The agent understands all three deliverables immediately and can issue three
file-creation calls in one model response.

Example C: Reasonable multi-agent case

    Review this large system for security vulnerabilities, performance
    problems, missing tests, and deployment risks.

Each area is a separate open-ended investigation that must decide what to do
based on what it discovers. Specialist agents may improve coverage and reduce
elapsed time.


12. RECOMMENDATION FOR THIS PROJECT
-----------------------------------

The normal /ask flow should remain single-agent because most requests are
connected codebase questions:

- Explain a feature
- Locate an implementation
- Diagnose a problem
- Trace an execution flow
- Compare two related components

The existing agent can already perform repeated and parallel tool calls when
useful.

Multi-agent behavior could later be added for special workflows:

    /ask         -> ordinary single-agent question
    /audit       -> multi-agent repository assessment
    /deep-review -> researcher, critic, and coordinator

For example:

    /ask Explain semantic caching

Use one agent.

    /audit Evaluate security, performance, tests, and deployment readiness

Consider several specialist agents.


13. ONE-SENTENCE INTUITION
--------------------------

Use one agent when one mind can follow the complete problem coherently, even if
it uses many tools. Use multiple agents when the problem contains several
substantial, independent, discover-as-you-go investigations whose separation
provides enough value to justify coordination.


14. INTERVIEW ANSWER
--------------------

"Parallel tool calling lets one agent execute multiple known operations at the
same time. Multi-agent architecture lets multiple independent reasoning loops
investigate different objectives at the same time. I use a single agent for
coherent /ask questions and would introduce multiple agents only for broad,
separable investigations, specialist permissions, or independent verification.
This avoids unnecessary cost, latency, and coordination complexity."



“Multi-agent architecture improves focus by giving each agent an isolated objective, context, and reasoning loop. For example, security and performance agents can investigate their domains independently and in parallel. However, that local focus introduces coordination and synthesis risks, so a coordinator is needed to preserve global coherence. I would use this design only when the request has substantial, separable areas; otherwise, one agent with multiple tools is simpler and more reliable. increased no of tokens could make too much noise and make model distracted”

extras:

Graph state: Information needed for the current workflow or conversation—messages, tool results, pending steps and approvals.
Long-term memory: Information intentionally retained across different sessions—such as the user’s preferences.
Checkpoint: A saved snapshot of graph state.
Checkpointer: The component that saves and reloads those snapshots.

Graph state is the workflow’s current notebook. A checkpoint is a saved photograph of that notebook stored in the database.
