MULTI-AGENT DAG ORCHESTRATOR - SIMPLE EXPLANATION
=================================================

1. THE MAIN IDEA
----------------


unfinished len==0. add it to ready_list

The system has one coordinator called the ORCHESTRATOR.

The orchestrator is normal Python code. It is not an LLM.
It decides:

- which task is ready;
- which task must wait;
- when to start a worker agent;
- when tasks may run concurrently;
- when to save a result;
- and when the entire plan is complete.

Worker agents do not directly call one another.
They do not need to know which agent runs next.

The flow is:

User -> Planner LLM -> SQLite -> Orchestrator -> Worker agents


2. WHAT HAPPENS WHEN THE USER ENTERS /plan
-------------------------------------------

Example:

    /plan Build a full-stack todo application

main.py recognizes the /plan command and sends the request to a planning
service. main.py should only route the command. It should not contain the DAG
logic.

The planning service calls a planner LLM. The planner returns structured
Pydantic data similar to this:

    Plan:
      A = Research the backend
      B = Research the frontend
      C = Implement the application; depends on A and B
      D = Test the application; depends on C

This creates the following DAG:

    A -----\
            > C -----> D
    B -----/

The application validates the DAG before saving it:

- every task ID must be unique;
- every dependency must exist;
- a task cannot depend on itself;
- the graph cannot contain a cycle;
- and the number of tasks must be within the configured limit. - doubt... 

If it is valid, the application saves the plan in SQLite and shows it to the
user. It does not execute anything until the user approves it.


3. WHY THERE ARE THREE TABLES
-----------------------------

Table 1: plans

One row represents one complete user request.

    plan_id | request                              | status
    --------+--------------------------------------+------------------
    plan-1  | Build a full-stack todo application  | awaiting_approval


Table 2: tasks

One row represents one unit of work.

    plan_id | task_id | title                 | status
    --------+---------+-----------------------+---------
    plan-1  | A       | Research backend      | pending
    plan-1  | B       | Research frontend     | pending
    plan-1  | C       | Implement application | pending
    plan-1  | D       | Test application      | pending


Table 3: task_dependencies

This table stores the arrows in the DAG.

    plan_id | task_id | dependency_task_id
    --------+---------+-------------------
    plan-1  | C       | A
    plan-1  | C       | B
    plan-1  | D       | C

Read each row like this:

    C depends on A
    C depends on B
    D depends on C

A and B have no dependency rows because they do not need to wait for another
task.

The third table exists because dependencies are a many-to-many relationship:

- one task can depend on many tasks;
- one task can also be required by many other tasks.

Keeping each dependency as a row makes it easy for SQLite to answer:

- Which tasks are ready now?
- What is task C waiting for?
- Which tasks must be blocked if task A fails?
- Does every dependency actually refer to a real task?

Dependencies could be stored as JSON inside the tasks table, but then checking,
indexing, and enforcing relationships would be harder. The separate table is
small and is the cleaner production design.


4. WHAT IS THE PRIMARY KEY?
---------------------------

The tasks table uses:

    PRIMARY KEY (plan_id, task_id)

This means plan-1/A and plan-2/A are different tasks.

The task_dependencies table uses:

    PRIMARY KEY (plan_id, task_id, dependency_task_id)

This prevents the same arrow from being saved twice. For example, it prevents
"C depends on A" from appearing twice in plan-1.

The ORCHESTRATOR queries it.

The planner LLM does not query it.
The worker agents do not query it.

The orchestrator asks the repository/storage layer for ready tasks:

    ready_tasks = plan_repository.find_ready_tasks(plan_id)

The repository runs a SQLite query whose meaning is:

    Give me pending tasks for which no dependency is unfinished.

At the beginning:

- A is ready because it has no dependencies.
- B is ready because it has no dependencies.
- C is not ready because A and B are not finished.
- D is not ready because C is not finished.

So the result is:

    ready_tasks = [A, B]

After A and B succeed, the orchestrator queries again. The result is:

    ready_tasks = [C]

After C succeeds, the next result is:

    ready_tasks = [D]


6. WHO SPAWNS THE AGENTS?
-------------------------

The orchestrator starts the worker agents.

Conceptually:

    while plan is not finished:
        ready_tasks = database.find_ready_tasks(plan_id)

        run independent research tasks concurrently
        run file-changing tasks one at a time

        save every result

The actual code would use a TaskRunner or AgentFactory owned by the
orchestrator:

    result = await task_runner.run(task, context)

For independent research tasks, it can use asyncio.gather:

    results = await asyncio.gather(
        run_task(A),
        run_task(B),
    )

That starts separate agent invocations for A and B at approximately the same
time. A concurrency semaphore should limit how many can run, for example three.

Because this design uses one shared working directory, agents that modify files
run one at a time. Running two writing agents concurrently could make them edit
the same file and overwrite each other.


7. HOW A TASK IS EXECUTED
-------------------------

For each ready task, the orchestrator performs these steps:

1. Atomically change its database status from pending to running.
2. Load the task description and summaries of its dependencies.
3. Build a small prompt for the appropriate worker agent.
4. Invoke the worker agent.
5. Validate the worker's result.
6. Save the summary and validation result.
7. Change the status to succeeded or failed.

The atomic pending-to-running update prevents the same task from being started
twice.


8. HOW SUMMARIES MOVE BETWEEN AGENTS
------------------------------------

Yes, summaries are passed through the database, but the orchestrator performs
the passing.

The agents do not send messages directly to each other.

Example:

Agent A returns:

    "The backend uses FastAPI. The main API module is app/api.py."

The orchestrator stores it in task A's result_summary column:

    plan_id | task_id | status    | result_summary
    --------+---------+-----------+------------------------------------------
    plan-1  | A       | succeeded | Backend uses FastAPI; API is app/api.py

Agent B returns a frontend summary, which is saved in the same way.

When C becomes ready, the orchestrator queries C's dependencies. It loads the
stored summaries for A and B and builds C's prompt:

    Your task:
    Implement the application.

    Information from completed dependency A:
    Backend uses FastAPI; API is app/api.py.

    Information from completed dependency B:
    Frontend uses React; routes are in src/routes.tsx.

    Acceptance criteria:
    - Backend and frontend communicate correctly.
    - Tests pass.

Only concise summaries and necessary artifact references are passed. Complete
agent conversations should not be copied into later agents.


9. WHAT HAPPENS WHEN A TASK FAILS?
----------------------------------

Suppose A fails permanently:

    A (failed) -----\
                    > C (blocked) -----> D (blocked)
    B (succeeded) -/

C cannot run because it requires A. D cannot run because it requires C.

The orchestrator marks C and D as blocked. An unrelated branch that does not
depend on A may still continue.

The failed task may be retried once. Validation feedback is included in the
retry prompt. There is no unlimited critic loop.


10. WHAT SQLITE IS DOING FOR US
-------------------------------

SQLite is the durable source of truth for the workflow.

If the application crashes after A finishes:

- A remains succeeded with its summary stored;
- B may already be succeeded too;
- C remains pending;
- /plan resume can continue with C instead of repeating A and B.

LangGraph's existing checkpointer continues storing conversation messages.
The new plans database stores workflow state. These responsibilities should
remain separate.


11. THE COMPONENTS IN CLEAN CODE
--------------------------------

main.py
    Recognizes /plan commands and displays results.

PlanningService
    Calls the planner, validates the Pydantic response, and saves the plan.

PlanRepository
    Is the only component that runs plan/task/dependency SQL queries.

DagValidator
    Checks missing dependencies, duplicate IDs, and cycles.

PlanOrchestrator
    Repeatedly finds ready tasks and controls execution order.

TaskRunner / AgentFactory
    Builds and invokes the correct worker agent for each task kind.

TaskValidator
    Runs tests, builds, type checks, or focused LLM review.

Finalizer
    Reads the completed task summaries and produces the final user response.

This separation keeps SQL out of agents and keeps orchestration logic out of
main.py.


12. THE COMPLETE EXAMPLE IN ONE VIEW
------------------------------------

1. User enters /plan Build a full-stack todo application.
2. Planner LLM returns tasks A, B, C, and D as a Pydantic PlanSpec.
3. DagValidator confirms that the graph is valid and has no cycle.
4. PlanningService writes the plan, tasks, and dependency rows to SQLite.
5. User approves the saved plan.
6. PlanOrchestrator queries PlanRepository for ready tasks.
7. Repository returns A and B.
8. Orchestrator starts research agents A and B concurrently.
9. Their results and summaries are saved to SQLite.
10. Orchestrator queries ready tasks again and receives C.
11. It loads A and B summaries and includes them in C's prompt.
12. Implementation agent C runs alone because it modifies files.
13. C is validated and its result is saved.
14. The next query returns D.
15. D runs the final verification.
16. Finalizer summarizes the entire plan for the user.

The most important rule is:

    The orchestrator controls agents.
    The database remembers state.
    The dependency table stores ordering rules.
    Agents only perform their assigned work.


13. EXACTLY HOW find_ready_tasks WORKS
--------------------------------------

The repository can use this SQL query:

    SELECT t.plan_id, t.task_id, t.title, t.status
    FROM tasks AS t
    WHERE t.plan_id = ?
      AND t.status = 'pending'
      AND NOT EXISTS (
          SELECT 1
          FROM task_dependencies AS d
          JOIN tasks AS parent
            ON parent.plan_id = d.plan_id
           AND parent.task_id = d.dependency_task_id
          WHERE d.plan_id = t.plan_id
            AND d.task_id = t.task_id
            AND parent.status <> 'succeeded'
      )
    ORDER BY t.task_id;

The ? is replaced safely with plan_id, for example plan-1.

The outer query first looks only at pending tasks from plan-1.

For each pending task, the inner query asks:

    Does this task have at least one dependency that has NOT succeeded?

NOT EXISTS reverses the answer:

    If an unfinished dependency exists, do not return the task.
    If no unfinished dependency exists, return the task.


FIRST QUERY: ALL TASKS ARE PENDING

For A:

- The dependencies table has no row where task_id is A.
- Therefore, no unfinished dependency exists.
- NOT EXISTS is true.
- A is returned as ready.

For B:

- The dependencies table has no row where task_id is B.
- Therefore, no unfinished dependency exists.
- NOT EXISTS is true.
- B is returned as ready.

For C:

- The dependency rows say that C requires A and B.
- A is pending and B is pending.
- At least one unfinished dependency exists.
- NOT EXISTS is false.
- C is not returned.

For D:

- The dependency row says that D requires C.
- C is pending.
- An unfinished dependency exists.
- NOT EXISTS is false.
- D is not returned.

The result is:

    [A, B]

The orchestrator can run A and B concurrently because both are research tasks.


SECOND QUERY: A FINISHED, B STILL RUNNING

Assume the task rows now look like this:

    A = succeeded
    B = running
    C = pending
    D = pending

A is not returned because it is no longer pending.
B is not returned because it is running.
C is not returned because B has not succeeded.
D is not returned because C has not succeeded.

The result is an empty list:

    []

This does not mean the plan is finished. It means the orchestrator must wait for
the currently running B agent.


THIRD QUERY: A AND B HAVE SUCCEEDED

The task rows are now:

    A = succeeded
    B = succeeded
    C = pending
    D = pending

C depends on A and B. Both parent tasks now have status succeeded, so the inner
query finds no unfinished dependency for C. C is returned.

D still depends on pending C, so D is not returned.

The result is:

    [C]


FOURTH QUERY: C HAS SUCCEEDED

The task rows are now:

    A = succeeded
    B = succeeded
    C = succeeded
    D = pending

D's only dependency, C, has succeeded. D is returned.

The result is:

    [D]


FINAL QUERY: EVERYTHING HAS SUCCEEDED

No task has pending status, so the result is:

    []

The orchestrator separately counts task statuses. If there are no pending or
running tasks and every task succeeded, it marks the whole plan succeeded.

    def find_ready_tasks(self, plan_id: str) -> list[TaskRecord]:
