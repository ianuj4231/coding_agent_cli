SIMPLE LONG-RUNNING DAG WORKFLOW
================================

GOAL
----
The user enters:

    /plan Build a full-stack application with HTML and CSS

The system creates a task plan, shows it in a table, and waits. Nothing runs
until the user clicks Yes. Independent tasks may run in parallel after approval.


MINIMAL FLOW
------------

    User request
        -> Planner LLM returns strict JSON
        -> Validate the DAG
        -> Show approval screen
        -> Save plan and tasks with the approval decision
        -> Yes: manager starts ready tasks
        -> No: mark plan rejected and run nothing

The manager is ordinary application code, not another free-thinking LLM. This
makes execution predictable and prevents agents from creating circular loops.


PLANNER OUTPUT
--------------
Ask the planner for JSON only. Keep each task small and outcome-focused.

    {
      "title": "Build a todo application",
      "tasks": [
        {
          "id": "backend",
          "prompt": "Build the API and data model",
          "depends_on": []
        },
        {
          "id": "frontend",
          "prompt": "Build the HTML and CSS interface",
          "depends_on": []
        },
        {
          "id": "integration",
          "prompt": "Connect the interface to the API",
          "depends_on": ["backend", "frontend"]
        },
        {
          "id": "verify",
          "prompt": "Run checks and report remaining problems",
          "depends_on": ["integration"]
        }
      ]
    }

Do not let the model provide task status, plan status, or execution commands.
The application owns those values.


VALIDATION BEFORE SAVING
------------------------
Reject the plan if:

- JSON does not match the required shape;
- a task ID is duplicated;
- a dependency names a missing task;
- a task depends on itself;
- the dependency graph contains a cycle;
- there are no tasks or there are more than a small configured limit.

Cycle checking happens once in application code before approval. At runtime the
manager only follows the already validated dependencies.


DATABASE: ONLY TWO TABLES
-------------------------

plans

    id | request | title | status

Plan status values:

    approved, rejected

tasks

    plan_id | id | prompt | depends_on | status | result

Task status values:

    pending(initial state-not started running yet) , running, completed, failed

Store depends_on as a JSON list. A separate dependency table is more relational,
but is unnecessary for this deliberately small first version. The manager can
load all tasks for one plan and calculate readiness in memory.

Use (plan_id, id) as the task primary key. Keep result short: a summary, useful
file paths, and any error. Do not store full agent conversations.


APPROVAL SCREEN
---------------
Show the generated plan as a table:

    Task        Work                              Depends on         Status
    backend     Build API and data model          -                  pending
    frontend    Build HTML and CSS interface      -                  pending
    integration Connect interface to API          backend, frontend  pending
    verify      Run checks                        integration         pending

Above or below it show:

    [Yes, start]  [No, reject]

Yes saves the plan as approved and starts the manager. No saves it as rejected.
Make approval a server-side decision; never trust a status sent by the browser.


MANAGER LOOP
------------
For a running plan, the manager repeatedly:

1. Loads its tasks.
2. Finds pending tasks whose dependencies are all completed.
3. Atomically marks those tasks running.
4. Runs the ready tasks concurrently, with a small concurrency limit.
5. Saves each result and marks it completed or failed.
6. Repeats until the plan is completed or failed.

If any task fails, stop scheduling new work. The failed task records the error.
A manual Retry button can reset only that failed task to pending later.

For the first version, only parallelize tasks that do not modify the same files.
An even safer rule is: research/design tasks may run in parallel; code-writing
tasks run one at a time. Relax this only after adding isolated branches or
worktrees.


LONG-RUNNING BEHAVIOR
---------------------
Use SQLite at .ia_claude_all_hidden/plans.db. The database is the source of
truth, so the web request does not need to remain
open. Run the manager in one background process. The UI polls a plan-status
endpoint every few seconds and redraws the table.

On process restart, look for approved plans with unfinished tasks. Change any
leftover running tasks back to pending, then resume the manager. This gives
simple crash recovery without introducing a queue system.

Run only one manager per plan. Claiming a task must be an atomic database update
from pending to running so the same task cannot start twice.


MINIMAL FILE SHAPE
------------------

    app.py          routes, approval endpoints, and status page
    planner.py      planner prompt, strict response parsing, DAG validation
    manager.py      ready-task selection and worker execution
    db.py           two-table storage operations
    templates/plan.html

Do not add separate factories, repositories, validators, event buses, or queue
services yet. Split a file only when it becomes genuinely difficult to maintain.


RECOMMENDED FIRST VERSION
-------------------------

- SQLite
- one background manager process
- two tables
- JSON dependency lists
- strict structured planner output
- Yes/No approval gate
- limited parallelism
- polling for UI updates
- stop-on-first-failure

This is enough for a clear, resumable DAG workflow without building a workflow
platform before the application needs one.
